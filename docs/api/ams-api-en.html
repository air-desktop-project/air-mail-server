The air-mail-server REST API

Developer manual. This API gives access to an account's mail and mailboxes, to message submission, and to server observability. It is served over HTTP/2 on TLS, and every request authenticates with a bearer token.

API version: v1 Token version: 0x01 Server: air-mail-server 0.2.7

1Overview

The air-mail-server REST API exposes four areas that have nothing to do with one another: reading your mail, submitting a message, administering the server, and watching its counters. That separation is not filing convenience — it is the foundation of the permission model described in §3.5.

1.1Surface

AreaWhat it allowsPrefix
mailList mailboxes, read messages and their MIME parts, set and clear flags, search/v1/mailboxes/…
submitSubmit a message for delivery or relay/v1/submissions
adminAccounts, addresses, domains, bans/v1/accounts/…, /v1/domains, /v1/bans/…
observeHealth and counters/v1/health, /v1/metrics

Two resources sit outside these areas because they act on yourself rather than on a server resource: /v1/tokens, which requires no permission because it is where you acquire one, and /v1/me/password, which requires only that you hold a valid token.

1.2Design principles

Three decisions shape everything else, and knowing them saves you from fighting the API.

A path is a designation, not a string

The server normalises nothing. An empty segment, a ., a .., a control byte, a malformed percent-escape, invalid UTF-8 — all are rejected rather than repaired. An ambiguous designation has no canonical form to choose; it has an author to say no to. This makes the classic failure inexpressible: a %2F that becomes a separator again after the access check.

Permission is demanded before it is granted

Every resource declares the scope it requires in the same table as the routing. There is no access-control list kept on the side — the kind that drifts out of step on the first addition, whose first symptom is a resource served without a permission check.

Nothing that goes out is concatenated

Almost everything this API returns came from elsewhere: a mailbox name a client chose, a subject a stranger wrote. Every representation goes through a single JSON encoder, and every fault through a single problem-document encoder.

2Transport and conventions

2.1TLS and HTTP/2

The API is served only over HTTP/2 on TLS. ALPN advertises h2 and nothing else: a client that cannot negotiate HTTP/2 will get no HTTP/1.1 fallback. There is no cleartext access, on any port.

Note

The listening address comes from the server's configuration. In a typical deployment the API answers on port 8443; ask your operator for the URL rather than assuming it.

2.2Paths

Every resource lives under /v1. The following limits apply to the path before anything else happens:

LimitValueOn overflow
Segments in a path8414 URI Too Long
Bytes per segment, after decoding255400 Bad Request
No query parameter is read

The string following a ? is split off the path and then discarded. No resource in this API currently accepts a query parameter — no filter, no sort, no pagination cursor. A request carrying them is not rejected: its parameters simply have no effect, which is more treacherous than a refusal. Do not build a client that depends on them.

2.3Media types

TypeWhere
application/jsonEvery request and response body except the two cases below
message/rfc822The body of a submission, and the response of …/raw
application/problem+jsonEvery error response, without exception

The server checks the body's type. For any protected resource it does so after authentication — a 400 about the content type would reveal that the path was recognised, and that is precisely the information §4 protects.

2.4Representations

  • Dates are numbers. Message arrival times are in seconds since the epoch; token expiry is in microseconds. The server never formats a date: the client is the one who knows who is reading it.
  • Empty and absent are distinguished. An empty subject is ""; a message with no subject is null.
  • UIDs are durable under a given uidValidity. Every response carrying UIDs also carries the mailbox's uidValidity (RFC 9051 §2.3.1.1). If it changes, your remembered UIDs no longer designate anything: discard your cache.
  • A truncated list says so. Rather than silently returning half, bounded or paginated resources carry a field that announces it.

3Authentication and security

This is the most important section of the manual. It describes what the server guarantees, what it does not, and where your share of the work begins. Read it in full before writing code against this API.

3.1The model on one page

  1. The client exchanges a login and password for a bearer token at POST /v1/tokens.
  2. The server verifies the credentials, then decides the scope on its own. The client does not request a scope and cannot obtain more.
  3. The token is sealed with HMAC-SHA-256 under a key only the server holds. It carries the account, the scope, an expiry and an identifier.
  4. Every subsequent request presents that token in Authorization: Bearer ….
  5. The server verifies the seal, only then reads the fields, then compares the token's scope against the one the resource requires.
The order is the guarantee

The seal is verified before a single field is interpreted. Reading an expiry before authenticating the token that carries it means trusting what you have not yet verified. The seal comparison runs in constant time.

3.2The bearer token

The token is an opaque base64url string. Do not parse it. Its internal structure may change; only the string matters to you.

Why this is not a JWT

A JWT carries its algorithm inside the token, in an alg field the verifier is expected to read in order to know how to verify. That is asking an unauthenticated message how to authenticate it, and two entire families of attacks live in that question: alg: none, which removes verification altogether, and the RS256 → HS256 confusion, which verifies a signature using a public key mistaken for a shared secret.

This token has no algorithm field. Its version fixes exactly one, and there is only one version. There is nothing to negotiate, and therefore nothing to confuse.

What it carries

FieldPurpose
VersionOne byte, 0x01. It fixes the sealing algorithm.
AccountThe name the bearer acts under. At most 64 bytes.
ScopeEight bits: two per area, read then write.
ExpiryMicroseconds since the epoch.
IdentifierA random number distinguishing this token from others of the same account.
SealHMAC-SHA-256 over everything above, 32 bytes.

The sealing key is at least 32 bytes. A key shorter than the seal it produces would give less security than the seal's size suggests.

3.3Obtaining a token

POST /v1/tokens no scope required

The body is a JSON object with two fields, both mandatory:

{ "login": "marie", "password": "…" }

Response 201 Created:

{
  "token":   "AQECAAAAAG…",
  "expires": 1790209932000000
}

expires is in microseconds since the epoch, not seconds. It is the only date in this API in that unit; message dates are in seconds.

No escapes in credentials

The server reads login and password without decoding JSON escape sequences. A password containing \n, \" or é will not be read as you wrote it. Use characters that need no escaping, or expect a refusal.

A refusal never says why

An unknown login and a wrong password produce exactly the same response: 401 Unauthorized, with the same error document. Distinguishing them would make the account file enumerable without knowing a single password. Do not build a UI that claims to tell them apart: it would be lying.

A failure counts against you

Every credential failure is recorded by the server's abuse guard as an invalid frame. Past a threshold, your address is banned and receives no response at all — not even a refusal. A client that retries in a loop after a 401 bans itself. Stop at the first refusal and ask the user for fresh credentials.

3.4Presenting a token

GET /v1/mailboxes HTTP/2
authorization: Bearer AQECAAAAAG…

Bearer is the only recognised scheme (RFC 6750). An authentication failure returns 401 Unauthorized together with www-authenticate: Bearer, which tells the client how to present itself.

Two distinct causes lead to 401, and the server deliberately distinguishes them in the error document's title:

CauseWhat you should do
The token does not verify — seal, structure or encodingDo not retry with the same token. Perform a fresh credential exchange.
The token is authentic and its time has passedRe-authenticate. This is the normal end-of-session case.

The second case is distinguished because it is only reachable after a valid seal: saying so teaches a forger nothing, and teaches an honest client that it should re-authenticate rather than believe its token rejected.

3.5Scopes

A scope is an area × right pair. The four areas are mail, submit, admin and observe; the two rights are read and write. Write contains read, not the other way round.

The scope a request requires is computed simply:

  • the area comes from the path;
  • the right comes from the verb: GET, HEAD and OPTIONS require read; POST, PUT, PATCH and DELETE require write.

What a password grants

A successful credential exchange always returns exactly this scope, and only this one:

AreaRight granted
mailwrite
submitwrite
observeread
adminnone
A password never opens administration

This limit lives in the server's code, not in a configuration. A setting would eventually be flipped, and a compromised account would then become the whole server. No combination of credentials, whatever rights the user holds elsewhere, produces an administration token through the API.

One practical consequence is worth knowing before you discover it: the client does not choose its scope. There is no scope parameter on the token request. You cannot ask for a read-only token for a dashboard — you get the full scope above, or nothing.

3.6Administration

An administration token is minted on the server machine, by whoever can already read its configuration:

air-mail-admin token /var/lib/air-mail/air-mail.conf \
                --login marie --minutes 30

That is the same authority as the one that can stop the service or read the mailboxes: no new authority is introduced. The name given need not designate an existing account — it says who is acting, and appears in what the server logs.

Treat it as a production secret

This token opens accounts, addresses, domains and bans. Give it the shortest lifetime that suffices, do not write it into a versioned configuration file, and do not pass it as a command-line argument on a shared machine — it would appear in the process table.

3.7What the API does

  • It authenticates every request independently of the previous ones. There is no server-side session.
  • It verifies the seal before reading anything, in constant time.
  • It bounds a token's life — fifteen minutes in service, twelve hours at most that the format allows — both at issuance and at verification.
  • It revokes a session, and then refuses the token that carried it.
  • It refuses what it does not understand rather than normalising it: ambiguous paths, JSON that parsers disagree about, excessive nesting.
  • It gives the same answer to "this resource does not exist" and "you are not allowed to know".
  • It counts abuse and bans sources that cross the thresholds.
  • It checks that an account writes only in its own name at submission, and reports any impersonation attempt to the operator.

3.8What the API does not do

This list matters as much as the previous one. Each item is either a responsibility that falls to you, or an expectation you should not hold.

Revocation exists, and here is its exact reach

The server keeps a registry of live sessions. A token is accepted only if its session is listed, and DELETE /v1/tokens/current removes it: the token stops holding on the next request.

A server restart closes every session. The registry lives in memory, and that is deliberate: a list of revocations lost on restart would give validity back to tokens someone meant to kill. Here the failure falls on the right side — everyone re-authenticates.

An administration token, however, stays irrevocable

It is minted out of band by air-mail-admin token and opens no session: there is nothing to close. It holds until its hour, whatever happens — which is why the tool mints it short by default, fifteen minutes.

What does not existWhat that means for you
Refresh tokenThere is none. On expiry you must perform a full credential exchange — so you must keep the means to do so, or ask the user again.
Client-chosen scopeYou cannot obtain a read-only token. If your component only needs to read, containing it is your architecture's job.
Query parametersNo filter, no sort, no cursor. See §2.2.
Usable paginationMessage listings return a next cursor but offer no way to send it back. It tells you there is more; it does not let you reach it.
CORS headersThe server emits no access-control-allow-origin and no preflight response. This API is not callable from a browser cross-origin. Go through your own service.
Advertised rate limitsNo header tells you how many requests remain. The guard bans without warning; keep to a reasonable pace.
Concurrency controlNo ETag, no If-Match. Two clients modifying the same resource overwrite each other silently.
Idempotent writesNo idempotency key. A replayed submission delivers a second message.
Accessible audit logThe server logs, but the API does not expose that log.

3.9Your responsibilities

What the server cannot do for you, because it has no say in it.

Storing the token

A bearer token is a secret equivalent to the password for as long as it lives, and it is not revocable. You must:

  • keep it out of any storage readable by other code: no localStorage in a browser, no world-readable file, no environment variable of a shared process;
  • never write it to a log, a stack trace, a crash report or a URL — a URL ends up in the logs of every intermediary;
  • erase it from memory as soon as the session ends.

Lifetime

A token lasts fifteen minutes in the configuration in service. Twelve hours is the ceiling the format allows, not the deployed value — hard-code neither: read expires, and design your client to survive re-authentication.

Certificate validation

You must validate the server's TLS certificate. Disabling that check — an --insecure, a verify=False — cancels the whole of this protection: the token then travels in the clear to whoever has placed themselves in the middle. No property in this section survives it.

Handling errors

  • Do not retry a 401 in a loop: you will get yourself banned.
  • Infer nothing from a 404: it means "this does not exist" or "you are not allowed to know". The two are indistinguishable by construction.
  • Respect a 503: it is temporary and your request may well succeed later.

The content you display

Subjects, senders and message bodies come from strangers. The server returns them decoded and correctly escaped for JSON — it does not return them safe to display. Escaping for your presentation layer remains entirely yours.

What you submit

At submission you compose the RFC 5322 message yourself. The server checks that the From: belongs to the authenticated account and refuses otherwise, but it fixes neither your MIME encoding nor your headers.

4Error model

Every fault, without exception, returns an RFC 9457 document with media type application/problem+json:

{
  "type":   "/problems/not-found",
  "title":  "no such resource",
  "status": 404
}

type is a relative reference, to be resolved against the document's URL (RFC 9457 §4.2.1). The server does not write it absolute because it does not know the name under which it is reached — a proxy can change that without telling it.

The type comes from the status, not the cause

Two causes sharing a status code necessarily share a type. This is deliberate: "this resource does not exist" and "your token does not open this scope" both answer 404, and a distinct type would immediately restore the distinction that the status code had just erased. Branch on status, not on title, which is meant for a human.

StatusTypeWhen
400/problems/bad-requestRejected path, unreadable or ambiguous JSON, unreadable message, invalid account body
401/problems/unauthorizedToken missing, unreadable, badly sealed, or expired. Carries www-authenticate: Bearer
403/problems/forbiddenOnly: the current password supplied during a secret change does not match
404/problems/not-foundThe resource does not exist, or your token does not open the scope it requires
405/problems/method-not-allowedThe resource exists but not with this verb. Carries allow
414/problems/uri-too-longMore segments than the server retains
500, 501, 503/problems/internalA server-side fault. A 503 is temporary and worth retrying
403 is rare, and it is not a permission failure

A missing permission returns 404, never 403. The only 403 in this API means "the current password you supplied is wrong": the bearer is acting on their own resource, whose existence they obviously know, and a 404 would send them looking in the wrong place.

5Resource reference

The scope shown is the one for a read; a write on the same resource requires the write right of the same area.

5.1Tokens

POST/v1/tokensnone

Exchanges credentials for a token. See §3.3.

DELETE/v1/tokens/currentvalid token

Closes the session the presented token carries, and returns 204. The token is refused by every later request, with 401.

An already-closed session returns 401: the token no longer holds, so it no longer opens even the door that would close it.

5.2Invitation and enrolment

This is how key-based authentication is bootstrapped: an operator mints an invitation, and the user redeems it to enrol the public key of their first device. Further devices will come through cross-enrolment, from a device already enrolled.

Enrolment alone ships; opening a session with the key does not

An enrolled key can be listed and revoked under /v1/me/devices, but nothing authenticates with it yet: challenge–response comes next. For now, authentication is still by password.

POST/v1/invitationsadmin:write
{ "login": "marie", "minutes": 1440 }

minutes is optional — 1440 (twenty-four hours) by default, 2880 at most. An invitation lives longer than a token because it travels by a human channel: its bearer needs time to install an application.

HTTP/2 201
{ "invitation": "AgAABp…", "login": "marie", "expiresAt": 1790086400 }

An account that does not exist returns 404: an invitation for a misspelt name would otherwise only surface at enrolment — that is, at a user who can do nothing about it.

An invitation is a bearer credential

Whoever holds it can enrol a key on that account. Send it over a channel you consider safe, and be aware that nothing attests that the person redeeming it is the person you gave it to. That is the limit of this mechanism, and the reason it is short-lived and single-use.

POST/v1/devicesnone
{ "invitation": "AgAABp…",
  "publicKey": "BB4YUy_UdUwC8wQdnHXOszuD_9gax85P6ILMscmLxYlupGwxHE4v9A3ZajZT5uRURdMt_khuztdcepDGoYiBwKM",
  "name": "Marie's iPhone" }

No Authorization header: the invitation is what authorises. Together with /v1/tokens, this is the only resource in this API reached without a token — and for the same reason: whoever is enrolling has nothing yet.

publicKey is an ECDSA P-256 key in SEC 1 uncompressed form (§2.3.3) — the byte 0x04 then x and y, sixty-five bytes — written in base64url without padding. name is optional.

HTTP/2 201
{ "id": "6b86b273ff34fce1…", "login": "marie",
  "addresses": ["marie@example.com"] }

The addresses come back here because the application has no token yet to ask for them. The id is the SHA-256 digest of the public key, in sixty-four hexadecimal digits: it needs no randomness, it is unique by construction, and it is already the fingerprint that cross-enrolment will need.

The name may be escaped — the invitation and key may not

Many JSON encoders escape non-ASCII by default: Python's standard encoder writes "T\u00e9l\u00e9phone" rather than "Téléphone". The name field accepts both spellings and treats them as one.

The invitation and publicKey, by contrast, are never escaped: their alphabet is that of RFC 4648 §5, which holds nothing a JSON encoder would escape. Accepting escapes there would open no use.

A name longer than 128 bytes once unescaped returns 400, without consuming the invitation.

An invitation is only good for the FIRST device

It is not consumed by a registry: it stops being valid because the account now has a device. Replaying the same invitation — even one still within its lifetime — returns 409 with /problems/conflict.

Operational consequence: re-inviting someone requires revoking their devices first. That is the right hygiene after a lost phone, and an inconvenience until cross-enrolment ships.

CodeWhen
401Invitation forged, expired, missing, or a bearer token presented in its place. All four answer alike.
400The key is not a point on the curve, or is the wrong size.
409This account already has an enrolled device.
404The invitation's account no longer exists.
501This server has no device store configured.

5.3Opening a session with a key

Once a device is enrolled, its key replaces the password: the server issues a challenge, the device signs it, and the server returns the same token as POST /v1/tokens. Nothing downstream changes — the token is used, revoked and expires identically.

What the server knows, and what it does not

Face ID and Touch ID unlock a local key. The server only sees a signature: it will never know "the user placed their finger", it knows "a key I enrolled signed my challenge". Biometrics are a promise made by the client.

POST/v1/sessions/challengenone
{ "login": "marie", "deviceId": "6b86b273ff34fce1…" }
HTTP/2 201
{ "challenge": "AwAAaN1…",
  "role": "ams-session",
  "serverIdentity": "mail.narro.ch",
  "expiresInSeconds": 60 }

No Authorization header: this is the third entry point of this API.

A challenge is issued even for a device that does not exist

Deliberately so. Refusing to issue one for an unknown id would make this route an enumeration oracle: you would only have to see which one gets a challenge. A challenge issued for an unknown device leads nowhere — no signature can ever match it.

The server returns the role and its serverIdentity alongside the challenge so the client need not guess them — and above all so that five native applications do not guess them differently.

POST/v1/sessionsnone
{ "challenge": "AwAAaN1…", "signature": "MEUCIQ…" }

signature is an ECDSA P-256 signature in fixed form — r ‖ s, sixty-four bytes — written in base64url without padding. DER is not accepted: platforms disagree on the serialisation, and reading two grammars over the same bytes is an ambiguity this server refuses. A client holding DER converts it; that is three lines on their side.

What is signed is NOT the bare challenge 
digest = SHA-256( role ‖ 0x00 ‖ serverIdentity ‖ 0x00 ‖ challenge )

All three parts are taken exactly as returned, in ASCII, separated by null bytes. Without this binding, a signature obtained to open a session here would open one elsewhere, or serve another purpose. The null separators stop two different inputs from running together into the same byte string.

The signature covers that digest, not the message: sign the digest directly (sign_prehash, SecKeyAlgorithmECDSASignatureDigestX962SHA256, and their equivalents).

HTTP/2 201
{ "token": "AQ…", "expires": 1790086400000000 }

The same body as POST /v1/tokens, and the same scope: mail, submission, observability. Never admin — holding a phone is not the operator's authority.

A challenge is good for one use

Yet there is no registry of issued challenges. It is not the challenge that remembers, it is the device: opening a session records the date, and a challenge is only acceptable if it was issued after that date. Replaying the same challenge — even within its sixty seconds — returns 401.

Consequence: two sessions cannot open within the same second for one device. The second asks for a new challenge, one second later.

What a client should do with a 401

Retry ONCE, with a fresh challenge, after one second. If that fails too, treat it as a refused authentication and fall back to the password or to re-enrolment.

Why: two session openings started at the same time by one application — mail sync and push registration, say — compete for the same second, and the second one is refused as a replay. One second of waiting is always enough.

The server will not say which cause applied, and that is not an oversight: distinguishing a replay would reveal that a given device authenticated recently — and anyone can ask for a challenge for any id. The silence here is the same rule as everywhere else in this API.

CodeWhen
401 "expired"The challenge is more than sixty seconds old. Distinguished on purpose: a drifting client clock would otherwise produce failures nobody can explain.
401 "not acceptable"Forged challenge, unknown device, wrong or malformed signature, replay, or a token presented in place of a challenge. All six answer alike.
501This server has no device store, or does not know its own domain.

5.4Mailboxes

GET/v1/mailboxesmail:read
{ "mailboxes": [
    { "name": "INBOX", "messages": 716, "unseen": 12,
      "uid_next": 1793, "uid_validity": 1756900000 }
] }
GET /v1/mailboxes/{mailbox}mail:read

GET returns a mailbox's state, in the same shape as a list entry.

PUT creates the mailbox and returns 204. It is idempotent (RFC 9110 §9.3.4): replayed on a mailbox that already exists, it does not fault — the requested state is the state that is.

A mailbox DELETE is permanent

It removes the mailbox and what it holds, with no trash and no confirmation. A mailbox that had children has its mail removed and its name kept, as RFC 9051 §6.3.5 prescribes; the answer is the same 204.

5.5Messages

GET/v1/mailboxes/{mailbox}/messagesmail:read
{
  "uidValidity": 1756900000,
  "messages": [
    { "uid": 1792, "size": 1282, "received": 1790138347,
      "subject": "[SG50 Battery] Test Email", "from": "ofrou-sierre@narro.ch",
      "flags": ["seen"] }
  ],
  "next": 1741
}

A page holds at most 50 messages. next carries the UID of the first message not returned, or null if there are no more.

The cursor goes nowhere

next tells you messages remain, but no parameter lets you resume from it. On a mailbox with more than fifty messages, this resource will only ever give you the first fifty.

POST/v1/mailboxes/{mailbox}/messagesmail:write

Files a message into the mailbox — a draft, a sent copy, an import. The body is a message/rfc822 message, and the 201 response carries the UID obtained: {"uid": 1792}.

Filing is not sending

Nothing is routed, nothing is signed, nobody else receives it. This is IMAP's APPEND (RFC 9051 §6.3.12). To send, see §5.5. A message that cannot be parsed is refused rather than filed: a mailbox holding one would no longer be served over IMAP.

GETPATCHDELETE /v1/mailboxes/{mailbox}/messages/{uid}mail

Returns the message's decoded envelope, under {"uidValidity": …, "message": {…}}.

Flags are named as IMAP names them (RFC 9051 §2.3.2), not in lower case: \Seen, \Answered, \Flagged, \Deleted, \Draft, $MDNSent, $Forwarded, $Junk, $NonJunk, $Phishing. The set is closed: ten, and not one more.

PATCH sets and clears flags, and returns the message as it has become:

{ "add": ["\\Seen"], "remove": ["\\Flagged"] }

The same flag on both sides is refused with 400 — the request would contradict itself, and guessing would be worse than refusing.

A message DELETE is permanent

It returns 204 and the message is gone. Server-side this single gesture is worth two: the message is first marked \Deleted, then removed — the store refuses to remove what does not carry the mark on disk, so that a stale belief never loses mail.

GET/v1/mailboxes/{mailbox}/messages/{uid}/rawmail:read

The message exactly as it arrived, as message/rfc822. This is not an alternative representation of the previous resource: one is what was received, the other is our reading of it. The question "what did the server actually receive?" must have a stable answer that does not depend on an Accept header.

GET/v1/mailboxes/{mailbox}/messages/{uid}/parts/{part}mail:read

One MIME part, numbered as RFC 9051 §6.4.5 prescribes — 1, 1.2, 2.1.1.

5.6Search

POST/v1/mailboxes/{mailbox}/searchmail:read

Search is a POST rather than a GET: its criteria do not fit unambiguously in a query string, and putting them there would have every intermediary log them.

{ "seen": false, "from": "narro.ch", "subject": "alert" }
CriterionTypeApplies to
seen, answered, flagged, deleted, draftbooleanThe flag, set or cleared
from, to, subjecttextThe corresponding header field
bodytextThe body
texttextHeader and body (RFC 9051 §6.4.4)

Criteria combine with AND, and there is no other way. No OR, no NOT: an expression language would require a tree, a bounded depth and a grammar of its own.

{ "uids": [1792, 1788, 1741], "uidValidity": 1756900000, "complete": true }

complete is false when the list was truncated. A client ignoring it would act on half its results believing it had them all.

5.7Submission

POST/v1/submissionssubmit:write

The body is a complete RFC 5322 message as message/rfc822 — not JSON. Wrapping a message in a JSON string would double its size to say nothing more.

POST /v1/submissions HTTP/2
authorization: Bearer AQECAAAAAG…
content-type: message/rfc822

From: marie@example.com
To: john@elsewhere.test
Subject: hello

The message body.
An account writes only in its own name

The From: must belong to the account the token carries. A message asserting another address is refused with 400, and the attempt is reported to the operator as impersonation. This is not a politeness check: it, and not DMARC, is what stops a compromised account from writing in a colleague's name.

The server delivers to local recipients, queues what goes out, and DKIM-signs what it accepts, for the domains whose zone it holds. A delivery failure returns 503: it is temporary, and your message may well go through later.

5.8What is yours

These resources require no scope: they act on yourself, and the token presented already says who that is. Requiring admin would make them routes only an administrator could take, which is exactly what they exist to avoid.

PUT/v1/me/passwordvalid token
{ "current_password": "…", "password": "…" }
The current password is required, and that matters

Without it, a stolen token would let an attacker lock the rightful owner out of their mailbox permanently: a token theft would become an account theft. A wrong current password returns 403.

GET/v1/me/devicesvalid token
{ "devices": [
    { "id": "a1b2c3", "name": "Marie's iPhone",
      "enrolledAt": 1790000000, "lastSeenAt": 1790003600 }
] }

The devices whose public key is enrolled on this account. lastSeenAt is 0 for a device that has never opened a session — the field is written either way, so that no client has to tell "absent" from "zero".

The public key is not there

It is public and would cost no secret, but sixty-five base64 bytes teach nothing to someone trying to work out which of their three phones to revoke. A short fingerprint will come with cross-enrolment, where it has a job: confirming by sight the device being added.

An account with no device returns {"devices":[]}, not an error: that is the state of every account before its first enrolment. A server started without a device store returns 501 — a forgotten configuration must not look like an account that has enrolled nothing.

HTTP/2 501
{ "type": "/problems/not-implemented",
  "title": "this server does not serve this resource", "status": 501 }
Titles are shown here in English; the wire carries French

This manual translates the title member for readability. The server emits it in French, and §3.1.3 of RFC 9457 makes it advisory in any case: branch on type and status, never on title. A client that string-matches it will break on the first rewording.

A 501 is not an outage, and is not to be retried

It carries the 5xx class, but it does not say "our code failed": it says "this server does not serve that". Treat it as a missing capability — stop asking, do not offer the screen that goes with it — and not as a temporary unavailability.

DELETE/v1/me/devices/{id}valid token

Revokes a device. Returns 204 with no body. This is the operation that is urgent: a lost phone is removed within the minute, not on the next business day — which is why it does not require admin.

Someone else's device is "not found", not "forbidden"

The token's account is part of the lookup. Returning 403 for someone else's device and 404 for an id that does not exist would allow enumerating the server's devices, one id at a time. Both cases therefore return 404.

Revoking twice returns 404 the second time. RFC 9110 §9.3.5 allows this: what must be idempotent is the effect, and it is — the device is gone either way. Returning 204 to a revocation that removed nothing would suggest something had been removed.

5.9Administration

All of these require the admin area, which a password never grants. See §3.6.

The secret is a separate resource, and it cannot be read

No method returns a password hash: there is no representation of the account that contains one. That is the reason for the separation, not a presentation choice.

A ban entry carries the source, the prefix length and the time remaining:

{ "bans": [ { "source": "2001:db8::", "prefix": 64, "seconds": 1740 } ] }

The prefix length is not decorative: 2001:db8:: alone does not say that an entire /64 is banned, and an operator would believe they had banned a single machine.

5.10Observability

GET/v1/healthobserve:read
{ "status": "ok" }

It only says "yes". No version, no build date, no host name: that would be a server header under another name, and this is precisely the resource a scan queries first.

GET/v1/metricsobserve:read

A flat object of integer counters. Their names and number depend on the server version — do not hard-code the list you expect.

The JSON accepted is narrower than the RFC

The reader refuses anything parsers disagree about, even where the standard tolerates it. A JSON body often crosses more than one piece of software before it arrives here; if two of them do not read the same thing in the same bytes, a filter placed upstream protects a document the server will never see. Compose plain JSON: no duplicate keys, no exotic numbers, no deep nesting.

7End-to-end example

# 1. Exchange credentials for a token.
TOKEN=$(curl -sS --fail-with-body \
  -X POST https://mail.example.com:8443/v1/tokens \
  -H 'content-type: application/json' \
  -d '{"login":"marie","password":"…"}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["token"])')

# 2. List the mailboxes.
curl -sS --fail-with-body https://mail.example.com:8443/v1/mailboxes \
  -H "authorization: Bearer $TOKEN"

# 3. Read a page of messages.
curl -sS --fail-with-body \
  https://mail.example.com:8443/v1/mailboxes/INBOX/messages \
  -H "authorization: Bearer $TOKEN"

# 4. Submit a message.
curl -sS --fail-with-body -X POST \
  https://mail.example.com:8443/v1/submissions \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: message/rfc822' \
  --data-binary $'From: marie@example.com\r\nTo: john@elsewhere.test\r\nSubject: hello\r\n\r\nThe body.\r\n'
What this example does badly, and you should not copy

The token travels through an environment variable and ends up in shell history — acceptable for hand exploration, never for code. The password is in cleartext on the command line, so visible in the process table. And --fail-with-body is no substitute for reading the error document.
