air-mail-admin

contrôle et configuration d'air-mail-server

Synopsis

air-mail-admin <COMMANDE> [ARGUMENTS]
air-mail-admin [--help | --version]

Description

air-mail-admin est la seule porte d'entrée de la configuration d'air-mail-server, et le seul moyen d'inspecter ses magasins. Le serveur lui-même n'a aucune option de réglage.

Il n'y a ni fichier découvert, ni service à joindre : un seul chemin se devine, celui de la configuration.

Le chemin de la configuration se devine, les autres non

config show, token, audit et registre prennent /var/lib/air-mail/air-mail.conf quand on ne leur en nomme pas d'autre. Un chemin fourni reste prioritaire, et la plainte nomme toujours le chemin réellement tenté.

config write ne le devine pas, et refuse en disant pourquoi : elle remplace le fichier entier, et ce qu'elle ne nomme pas est effacé. Une commande incomplète tapée par habitude réécrirait la configuration vivante avec le seul jeu d'options frappé — dont le registre, sans lequel la réception refuse par 451.

Les magasins ne se devinent pas non plus — comptes, applicatifs, appareils, délégations, SCRAM, boîtes. Ils sont nommés dans la configuration, en absolu, et deux machines ne les rangent pas forcément au même endroit. Un défaut en dur finirait par mentir.

Un mot qui commence par deux tirets n'est jamais pris pour un chemin : c'est ce qui permet d'écrire registre cherche --limit 20 sans que --limit soit lu comme un nom de fichier.

Trois règles qui valent pour tout

1. Un secret ne passe jamais par la ligne de commande. account add, account passwd et toute pose de secret lisent le mot de passe sur l'entrée standard. Ce que ps(1) affiche, tout le monde le lit.

2. Lancez ces commandes sous le compte du service. Plusieurs commandes créent le fichier qu'elles nomment — un magasin, une clé — et le créent au nom de qui les lance. Créé par root, un magasin naît root:root 0600 et le serveur, qui tourne en air-mail, ne peut plus le lire. Il ne le dit pas : il répond 535 Authentication credentials invalid à chaque secret de ce magasin, exactement comme si le secret était faux, tandis que les autres continuent de marcher.

sudo -u air-mail air-mail-admin ...

et, pour s'en assurer, stat -c '%U:%G' sur le magasin.

3. La lecture ne modifie rien. config show, account list, app-password list, device list, audit, registre verifie, registre cherche et summary sont en lecture seule, sans danger sur une machine en service.

Commandes

Configuration

config write <fichier> [OPTIONS]

écrit une configuration binaire. C'est le seul moyen d'en produire une : le format n'est pas éditable à la main, et c'est délibéré.

Cette commande remplace le fichier entier. Une option absente de la ligne de commande est absente de la configuration écrite — donc effacée. Voir Réécrire une configuration vivante, qui n'est pas un conseil de prudence mais la seule procédure sûre.

config write --help liste les 89 options et dit, pour chaque seuil, où zéro veut dire « jamais » et où il veut dire « tout de suite ».

Et elle ne devine pas sa cible, à la différence des quatre autres familles : sans chemin, elle refuse par un code 2 et dit pourquoi.

config show [<fichier>]

relit une configuration et l'affiche, y compris ce qu'elle ne porte pas : « AUCUN MAGASIN », « NON SERVI », « aucune ». C'est la seule source de vérité sur ce qu'une machine porte. Le mot de passe du relais n'est pas affiché, et le secret de scellement non plus.

Comptes

account add <fichier> --login <nom> [--address <adresse>]...

ajoute ou remplace un compte. Le mot de passe se lit sur l'entrée standard. --address est répétable et donne les adresses qui arrivent dans cette boîte ; sans aucune, le compte se connecte mais ne reçoit rien.

Le nom du compte est aussi le nom de sa boîte : ni vide, ni ., ni .., sans /, sans point en tête.

account passwd <fichier> --login <nom>

change le seul mot de passe d'un compte existant, le secret venant de l'entrée standard.

À préférer à account add pour ce seul usage. add remplace le compte entier : sans ses --address, il efface les adresses — le compte s'authentifie encore et ne reçoit plus rien, sans que rien ne le dise. Et passwd refuse un compte inconnu sans toucher au magasin, là où une faute de frappe ferait créer par add un compte fantôme portant le secret qu'on croyait poser ailleurs.

account list <fichier>

liste les noms de comptes. Jamais les empreintes.

C'est lui qui tranche sur un login. Un login n'est pas une adresse, et deux serveurs ne nomment pas forcément le même compte de la même façon : la même personne peut être thierry.delhaise ici et thierry là. Lisez cette commande avant d'écrire un login dans une autre.

account remove <fichier> --login <nom> [--app-passwords <applicatifs>] [--delegations <délégations>]

retire un compte — et, si l'on nomme leur magasin, ses mots de passe applicatifs et ses délégations. Sans cela, un compte recréé sous le même nom en hériterait.

SCRAM

account add|passwd ... --scram-key <clé> --scram <fichier>

pose aussi un vérificateur SCRAM, dans un magasin séparé et scellé. Les deux options vont ensemble ou aucune : sans elles, SCRAM n'existe pas, ni annoncé ni stocké. Le vérificateur ne se dérive que du mot de passe en clair : un compte créé sans ces options n'en aura jamais tant que son mot de passe n'aura pas été reposé.

scram init <clé>

tire la clé de scellement du magasin SCRAM : trente-deux octets du noyau, en 0600. Rangez-la ailleurs que le magasin — c'est toute la raison d'être des deux fichiers. Refuse d'écraser une clé existante, une clé perdue rendant tous les vérificateurs illisibles.

scram bind <comptes> --scram-key <clé> --scram <fichier>

lie à l'empreinte actuelle de leur compte les vérificateurs écrits avant la 0.2.16, qui sans cela ne s'ouvrent plus. À lancer une fois après la mise à jour.

N'employez cette commande que si aucun mot de passe n'a été changé par l'API depuis la dernière dérivation : lier le vérificateur d'un ancien mot de passe le rouvrirait. En cas de doute, account passwd --scram redérive.

Mots de passe applicatifs

app-password add <applicatifs> --accounts <comptes> --login <nom> --name <nom>

crée un mot de passe applicatif : un secret par client de messagerie, révocable seul. Il ouvre IMAP, SMTP et POP3 en PLAIN, jamais l'API REST ni SCRAM.

Le secret est écrit une seule fois sur la sortie standard, et n'est rangé que sous forme de condensat : copiez-le. Et lancez cette commande sudo -u air-mail : elle crée le magasin s'il n'existe pas — voir les trois règles, plus haut.

app-password list <applicatifs> [--login <nom>]

liste identifiants, noms et dates. Jamais un secret.

app-password remove <applicatifs> --login <nom> --id <identifiant>

révoque un mot de passe applicatif, sur-le-champ.

Jetons et clefs

token [<config>] --login <nom> [--minutes <n>]

frappe un jeton d'administration et l'écrit sur la sortie standard. Il se scelle avec le secret que la configuration porte : donc depuis la machine du serveur, et par qui peut lire ce fichier.

Aucun mot de passe n'ouvre l'administration. C'est ce qui fait qu'un compte compromis ne devient jamais le serveur entier, et c'est pourquoi ce jeton se frappe ici. --minutes vaut 15 par défaut, et douze heures au plus.

vapid <chemin>

la clef VAPID de Web Push (RFC 8292) : créée si le fichier n'existe pas — trente-deux octets du noyau, en 0600 —, et jamais remplacée s'il existe. Écrit sa moitié publique en base64url, ce que les applications donnent au navigateur pour s'abonner. La remplacer désabonnerait tous les navigateurs.

Appareils

device list <magasin> [--login <nom>]

les appareils enrôlés : identifiant, nom, enrôlement, dernière session, attestation, abonnement.

device revoke <magasin> --login <nom> (--id <id> | --all)

révoque un appareil, ou tous ceux d'un compte — la voie de secours quand son titulaire les a perdus, une invitation ne valant que pour un compte sans appareil. Ses sessions cessent de valoir à la requête suivante.

Inspection

audit [<config>] --login <nom> [--limit <n>]

le journal d'audit du compte : sessions, refus, appareils, secrets, délégations, abonnements. Une ligne JSON par entrée, la plus récente d'abord, 50 par défaut. En lecture seule, depuis la machine du serveur.

registre verifie [<config>]

vérifie le registre de réception : chaque fichier entier, son sceau juste, et chacun chaîné au précédent. Une faute rend un code de sortie 1.

registre cherche [<config>] [--ip <adresse>] [--domaine <d>] [--message-id <id>] [--session <hex>] [--depuis AAAA-MM-JJ] [--jusqu-a AAAA-MM-JJ] [--limit <n>]

les enregistrements qui correspondent, une ligne JSON chacun, dans l'ordre du temps — les n derniers, 100 par défaut. --domaine cherche dans le HELO, le PTR, le MAIL FROM, le From et les domaines SPF, DKIM et DMARC. En lecture seule.

summary <maildir>

relit une boîte et rend ce que ses noms de fichiers portent : messages numérotés, messages à adopter, noms illisibles, et la réserve d'UID de l'index. En lecture seule — elle n'adopte rien et ne réécrit pas l'index, donc sans danger sur une boîte que le serveur tient ouverte.

Options de « config write »

Elles sont au nombre de 89, et air-mail-admin config write --help en est la référence exhaustive. Les recopier ici les ferait vieillir. Par famille :

Identité et boîtes

--domain, --hosted (répétable), --maildir, --accounts, --drafts.

Écoutes

--listen, --listen-smtps, --listen-imap, --listen-imaps, --listen-pop3, --listen-pop3s, --listen-http, --listen-h3.

Toutes en [::]:port : 0.0.0.0 est pris au mot depuis la 0.2.45 et ne sert que l'IPv4, ce qui ne se voit pas tant qu'on n'essaie pas en IPv6.

TLS et DKIM

--tls-cert, --tls-key, --dkim-selector, --dkim-key.

Le type de clé DKIM se décide avec la zone : une clé Ed25519 sous un enregistrement k=rsa échoue en silence.

Magasins

--scram, --scram-key, --devices, --app-passwords, --delegations.

Traces

--registre, --audit.

Sans registre écrivable, la réception refuse par 451 — ce n'est pas une option de confort.

Exigences sur l'enveloppe

--require-fqdn-helo, --require-fqdn-sender, --require-fqdn-recipient, --require-sender-domain.

Émission

--relay, --queue-spool, --relayhost, --relayhost-user, --relayhost-implicit-tls, et les quatre --queue-*-seconds.

Éteinte par défaut : ce serveur reçoit, il n'émet pas. Le mot de passe du relais se lit sur l'entrée standard.

SPF, DMARC, MTA-STS, TLSRPT

--spf, --dmarc, --resolver, --public-suffix-list, --dmarc-quarantine-folder, --dmarc-report-dir, --dmarc-send, --mta-sts-anchors, --mta-sts-cache, --tlsrpt-dir, --tlsrpt-send.

Garde et débit

--connections-per-minute, --commands-per-minute, --invalid-frames-per-minute, --refused-recipients-per-minute, --ban-seconds, --tracked-sources, --ipv4-prefix-bits, --ipv6-prefix-bits, --api-requests-burst, --api-requests-per-second.

Réveil des appareils

--push-vapid-key, --push-contact, les --apns-*, --fcm-service-account, et les attestations --android-* et --apple-*.

Divers

--about, --max-message, --max-connections, --command-timeout-seconds, --data-timeout-seconds, --quic-idle-seconds, --rotate-token-key.

Réécrire une configuration vivante

config write remplace le fichier entier, et deux choses qu'il porte ne se voient pas dans un config show. Les ignorer casse la production en silence.

1. Le mot de passe du relais n'est pas affiché. Une configuration réécrite avec un secret vide donne un diff(1) parfaitement propre — et l'émission cesse.

2. Le secret de scellement est tiré à neuf sur un fichier neuf. Tous les jetons d'API en cours cesseraient de valoir. Écrite sur une copie du fichier vivant, la configuration le reprend — et config write le dit : « secret REPRIS du fichier existant ».

La procédure sûre, dans cet ordre :

config show <vivante>              -> la référence
cp <vivante> <candidate>           # pour que le sceau soit REPRIS
config write <candidate> ...       # TOUT le jeu d'options
config show <candidate> | diff     # ne doit montrer QUE l'ajout
empreinte du secret de relais      # identique des deux côtés

puis, seulement alors : bascule, redémarrage, et retour arrière si le service ne repart pas.

Une commande de manuel vieillit sans prévenir. Le jeu d'options d'une machine en service grandit ; une commande recopiée d'une documentation ne porte que ce que la documentation savait le jour où elle a été écrite. La vérité du jour est config show, et rien d'autre.

Exemples

Poser le mot de passe d'un compte, sans qu'il passe par ps(1) :

printf %s "$SECRET" | sudo -u air-mail \
    air-mail-admin account passwd /var/lib/air-mail/comptes.bin \
    --login thierry.delhaise

Un mot de passe applicatif pour un téléphone :

sudo -u air-mail air-mail-admin app-password add \
    /var/lib/air-mail/applicatifs.bin \
    --accounts /var/lib/air-mail/comptes.bin \
    --login thierry.delhaise --name "iPhone"

Ce qu'une machine porte vraiment, et ce qui lui manque :

sudo -u air-mail air-mail-admin config show \
    /var/lib/air-mail/air-mail.conf

Retrouver au registre ce qui est arrivé d'un domaine :

sudo -u air-mail air-mail-admin registre cherche \
    /var/lib/air-mail/air-mail.conf --domaine example.net --limit 20

Diagnostics

Code de sortie 0 en cas de succès, non nul sinon. registre verifie rend 1 sur un sceau faux ou une chaîne rompue.

535 Authentication credentials invalid sur un mot de passe applicatif dont vous êtes sûr : vérifiez le propriétaire du magasin — voir les trois règles, plus haut.

Fichiers

Aucun chemin n'est implicite : tous sont nommés en argument. Par convention, sous /var/lib/air-mail : air-mail.conf, comptes.bin, scram.bin, appareils.bin, applicatifs.bin, delegations.bin, registre/, audit/, brouillons/, maildir/, file/.
